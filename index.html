What I owned

  • Input architecture. One player controller owns every Enhanced Input action and mapping context and re-broadcasts them as delegates, plus a layer that detects keyboard/mouse or gamepad, and which gamepad, at runtime.
  • UI. The HUD and every in-game menu (inventory, pause, options, controls, crafting, fast travel, tutorials, modals), driven by one HUD class that handles focus, menu stacking and the switch to menu input.
  • Generalist work. Debugging and optimisation across systems up to the Steam launch.

Input: gameplay never reads a key

Widgets and gameplay classes subscribe to what happened (interact, navigate, close menu), never to which key was pressed. A separate tracker watches the raw input stream so every button prompt in the game shows the right icon for the device in the player's hands.

1 · Raw inputFInputDeviceInputProcessor

Slate pre-processor. Sees every key and mouse move before any widget, consumes nothing.

2 · DeviceUInputDeviceTrackerSubsystem

Keyboard/mouse or gamepad, and Xbox, PlayStation or Switch through Steam Input.

3 · IconsUInputGlyphService

Maps logical actions to button icons from data assets set in Project Settings.

4 · UIPrompts, tutorials, controls tab

Subscribe to device changes and redraw their icons on the spot.

In parallel, AMainController binds the Enhanced Input actions and re-broadcasts them as delegates (OnInteract, OnNavigationMoveUp, OnCloseMenu…) that gameplay and menus listen to.

UI: one owner for every menu

AGameHUDSetUp creates every menu widget and is the only place that opens or closes them. It checks whether a menu may open, tracks the focused widget, applies toggle cooldowns and swaps the controller to the menu-navigation context while a menu is open. Widgets get data through events, not per-frame polling. UBaseWidget and UBaseButton give every screen the same open/close flow, focus handling and hover animations, so mouse and gamepad navigation feel the same.

What I would do differently

SetInputContext() clears every mapping and applies a single context, so an overlay cannot add input on top of the current mode. Next time I would use a context stack with priorities. AGameHUDSetUp also grew into one class that knows every menu; I would split it into a generic menu stack (or CommonUI activatable widgets) where new screens register themselves.
